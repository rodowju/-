# 기술 아키텍처 v0.1

GDD v0.1 기준. 버전 번호와 외부 서비스 조건은 구현 시점에 재확인한다 (이 문서 작성 시 미검증).

## 1. 핵심 원칙
1. **시뮬레이션 코어 분리:** 게임 규칙은 렌더링·DOM·네트워크를 모르는 순수 TypeScript 패키지. 클라이언트와 서버가 같은 코드를 실행한다.
2. **결정론:** 같은 `(시드, 입력 로그)` → 항상 같은 결과. 리플레이, 봇, 서버 검증, 고스트의 공통 기반.
3. **입력은 이벤트 로그:** 상태가 아니라 `(tick, down|up)`만 저장/전송한다.
4. **단계적 확장:** MVP는 서버 없이 완결. 서버는 코어를 재사용해 얹는다.

## 2. 기술 선택

| 영역 | 선택 | 근거 / 대안 |
|---|---|---|
| 언어 | TypeScript (strict) | 코어 공유, 타입 안정성 |
| 렌더링/엔진 | **Phaser 3** | 모바일 2D 웹 생태계, 입력/오디오/씬 내장. 대안 PixiJS(더 가볍지만 직접 구현량 증가). 번들 크기와 60fps는 프로토타입에서 측정 후 확정 |
| 빌드 | Vite | 빠른 HMR, 코드 분할 |
| 모노레포 | pnpm workspaces | 코어 공유 |
| 테스트 | Vitest | 코어 단위 테스트, 결정론 회귀 테스트 |
| PWA | vite-plugin-pwa | 설치/오프라인 캐시. 스토어 필요 시 Capacitor 래핑 검토 |
| 클라이언트 호스팅 | Vercel (정적) | 아래 §7 |
| 서버 (2단계 이후) | Node + WebSocket (Colyseus 후보) | §6 |

## 3. 디렉터리 구조
```
/
├─ packages/
│  └─ sim/                     # 순수 시뮬레이션 코어 (의존성 0)
│     ├─ src/
│     │  ├─ config.ts          # 물리/판정 상수 (GDD §4.3)
│     │  ├─ rng.ts             # 시드 PRNG
│     │  ├─ guardian.ts        # 술래 사이클 상태머신
│     │  ├─ runner.ts          # 가속/제동, 위치
│     │  ├─ judge.ts           # Watch 판정, Close Call 등급
│     │  ├─ bots.ts            # 시드 기반 봇
│     │  ├─ stage.ts           # 스테이지 파라미터 생성
│     │  ├─ world.ts           # step(state, inputs) → state
│     │  └─ replay.ts          # 입력 로그 → 재현, 직렬화
│     └─ test/
├─ apps/
│  ├─ client/                  # Phaser + Vite
│  │  ├─ src/
│  │  │  ├─ scenes/            # Boot, Play, Result, Replay, Shop
│  │  │  ├─ render/            # sim 상태 → 스프라이트 (읽기 전용)
│  │  │  ├─ input/             # 터치 → InputEvent 변환
│  │  │  ├─ audio/             # 박자 클록 동기
│  │  │  ├─ services/          # 광고, 저장소, 분석, i18n
│  │  │  └─ ui/
│  │  └─ public/               # 에셋
│  └─ server/                  # (후속) 룸/매치, 입력 검증
├─ docs/
└─ package.json / pnpm-workspace.yaml
```

의존성 방향: `client → sim`, `server → sim`. `sim`은 아무것도 import하지 않는다 (DOM, Phaser, Node API 금지).

## 4. 시뮬레이션 코어 설계

### 4.1 고정 타임스텝
- `TICK_HZ = 60`, 시뮬레이션 시간은 **tick 정수**로만 센다. `Date.now()`, `performance.now()` 사용 금지.
- 클라이언트는 누산기(accumulator)로 렌더 프레임과 tick을 분리한다.
- 렌더는 이전/현재 상태를 **보간**한다. 상태를 직접 바꾸지 않는다.

### 4.2 결정론 규칙
- 난수는 시드 PRNG(예: mulberry32 계열)만 사용. `Math.random` 금지.
- 시간 단위는 정수(ms 또는 tick). 속도/위치는 **정수 고정소수점**(예: 1/1000 단위)으로 보관해 부동소수점 편차를 회피한다.
- `Math.sin` 등 구현 의존 함수는 코어에서 사용하지 않는다.
- 컬렉션 순회 순서 고정 (봇 ID 오름차순).
- CI에 결정론 회귀 테스트: 고정 시드 + 고정 입력 → 최종 상태 해시 일치.

### 4.3 데이터 모델 (개략)
```ts
type Tick = number;
type InputEvent = { tick: Tick; type: 'down' | 'up' };

interface StageSpec {            // 시드로부터 결정
  seed: number;
  trackLength: number;           // 고정소수점
  chantTicks: number[];          // 사이클별 길이
  watchTicks: number[];
  botCount: number;
}

interface WorldState {
  tick: Tick;
  guardian: { phase: 'chant'|'turn'|'watch'|'turnback'; phaseStart: Tick; cycleIdx: number };
  runners: RunnerState[];        // [0] = 플레이어, 나머지 봇
  combo: number; score: number;
  events: SimEvent[];            // 이번 tick 이벤트 (Perfect, Caught 등) → 연출용
}

function step(state: WorldState, spec: StageSpec, inputs: InputEvent[]): WorldState;
```
`step`은 순수 함수. 연출·사운드·햅틱은 `events`를 소비해 트리거한다.

### 4.4 리플레이
- 저장 단위: `{ stageSpec, inputs[] }` (수 KB 이하). 최근 3초 재현은 해당 구간 직전의 스냅샷 + 입력으로 처리.
- 탈락 리플레이: `Caught` 이벤트 tick 기준으로 3초 전 스냅샷부터 재생, 마지막 0.5초는 시간 스케일 0.5.
- 스냅샷은 매 N tick 저장하는 링 버퍼(약 5초분).

## 5. 클라이언트 구조
- **Scene 흐름:** Boot → Play(스테이지) → Result → (Replay 오버레이) → 다음 스테이지/Shop.
- **입력 계층:** 포인터 이벤트를 즉시 `InputEvent`로 변환해 현재 tick에 기록. `touch-action: none`, 포인터 캡처로 홀드 이탈 방지.
- **오디오 동기:** 박자 클록은 WebAudio의 `currentTime` 기준. 시뮬레이션 tick과의 오프셋을 보정값으로 저장하고, 설정에 **입력/오디오 지연 보정 옵션** 제공.
- **저장:** localStorage/IndexedDB (코인, 진행, 설정, 스킨). 키-값 버전 태그로 마이그레이션 대비. 계정 연동은 후속.
- **서비스 인터페이스:** `AdsService`, `Analytics`, `Storage`, `I18n`을 인터페이스로 두고 구현체를 주입한다 (SDK 교체·웹/네이티브 분기 대비).

### 성능 예산 (목표, 측정 필요)
| 항목 | 목표 |
|---|---|
| 프레임 | 중급 모바일 60fps |
| 초기 번들 | < 3MB |
| 오브젝트 | 러너 13명 + 술래 + 배경 (스프라이트 아틀라스, 오브젝트 풀) |
| GC | 프레임당 할당 최소화 (코어는 상태 재사용 또는 얕은 복사) |

## 6. 멀티플레이 (M6 구현)

> v0.1 의 6장(보상 창 100~150 ms, Colyseus 후보)은 아래 결정으로 **대체**되었다. 변경 이유를 함께 남긴다.

### 6.1 구성
| 패키지 | 역할 |
|---|---|
| `packages/sim` | `RollbackWorld`: 입력 추가·교체·제거 시 해당 tick 으로 되감아 재시뮬레이션. 다인원(`spec.humans`), 러너별 점수/콤보 |
| `packages/net` | 프로토콜(메시지 검증), 입력 수락 정책, 시계 동기화, **클라이언트 넷코드 엔진 `NetSession`**, 고스트 검증 |
| `apps/server` | Node + `ws`. 매치메이킹, `MatchRoom`(서버 권위), 고스트 HTTP API |
| `apps/client` | `OnlineScene`(대전), 고스트 경주·업로드, `WorldView`(싱글/온라인 공용 렌더러) |

### 6.2 넷코드: 입력 릴레이 + 롤백 + 서버 권위
- 시뮬레이션이 결정론적이므로 **입력만** 주고받는다(대역폭 매우 작음). 서버도 같은 `RollbackWorld`로 상태를 계산하며, 서버 결과가 최종이다.
- 클라이언트는 서버보다 `lead` tick 앞서 실행한다(편도 지연 + 지터 + 여유). 그래서 내 입력이 서버에 "제때" 도착하고 즉시 반응한다(예측).
- 서버가 확정한 tick 이 예측과 다르면 교체·롤백한다. 다른 사람의 입력은 도착하는 대로 과거 tick 에 끼워 넣고 롤백한다.
- 서버는 30 tick 마다 **확정 tick 의 상태 해시**를 보낸다. 클라이언트가 비교해 어긋나면 전체 입력으로 재구성한다(재동기화). TCP 순서 보장 덕분에 해시보다 먼저 관련 입력이 도착한다.
- 경기 종료 시 서버 최종 상태 해시와 로컬을 비교해 `endVerified`로 기록한다.

### 6.3 지연 공정성 결정 (v0.1 변경)
| 항목 | v0.1 제안 | M6 결정 | 이유 |
|---|---|---|---|
| 과거 입력 허용 | 100~150 ms 보상 창 | **2 tick(≈33 ms)** | 반응 게임에서 넓은 보상 창은 "늦게 보고 과거 시점으로 릴리즈"하는 시간 되돌리기 치트를 그만큼 허용한다 |
| 늦게 온 입력 | 과거 tick 에 적용 | **현재 tick 으로 밀고 `late` 표시** | 지연이 큰 유저 본인만 불리하고, 다른 사람은 영향 없음. 결과 화면에서 원인을 안내 |
| 지연 흡수 | 서버 보상 | **클라이언트 리드** | 정상 유저는 입력이 제때 도착하므로 보상 창이 필요 없다 |
| 프레임워크 | Colyseus 후보 | **`ws` 직접** | 상태 동기화가 아니라 입력 릴레이 구조라 Colyseus 의 상태 스키마가 필요 없다 |

검증 결과(Node 통합 테스트, 실제 WebSocket, 순서 보존 지연·지터 주입):
- 게임 시간 기준 편도 60±40 ms: 늦은 입력 0, 동기화 오류 0
- 게임 시간 기준 편도 240±160 ms: 동기화 오류 0, 일부 입력만 `late`. 불이익은 지연된 본인에게만 간다
- 롤백 코어: 입력이 최대 200 tick 늦게·뒤섞여 도착해도 처음부터 다 알았을 때와 비트 단위로 같다(무작위 50회)

### 6.4 매치메이킹
- 요청 스테이지를 난이도 구간 대표 스테이지(3/10/20/30)로 묶어 매칭한다. 룸당 최대 4명이다.
- 첫 참가자 이후 대기 시간(기본 8 s)이 지나면 인원이 덜 차도 시작하고, 빈자리는 봇이 채운다(총 러너 수 유지).
- 매치마다 서버가 시드를 새로 정한다. Assist 는 0 이다(공정).
- 누른 채로 나가면 손을 뗀 것으로 처리한다. 남은 사람이 모두 끝나면 종료하고, 최대 3분이다.

### 6.5 고스트(비동기 대전)
- 클리어 시 입력 로그를 업로드한다(통계 끄기 설정을 따름). 서버는 **기준 시드로 직접 재시뮬레이션**해 완주를 확인하고, 시간·점수를 스스로 계산한다. 클라이언트가 보낸 결과는 받지 않는다.
- 스테이지별 빠른 순 상위 100개를 보관한다. 같은 기록은 중복 저장하지 않는다.
- 고스트 선택: "목표(par) 이하 중 가장 느린 기록", 즉 조금만 더 하면 이길 수 있는 상대다.
- 공식 리더보드는 **Assist 0 기록만** 올린다(보조받은 기록과 섞지 않음).

### 6.6 부정행위 방지 현황
| 위협 | 대응 | 상태 |
|---|---|---|
| 속도·결과 조작 | 서버가 입력으로 재계산 | 구현 |
| 시간 되돌리기(과거 스탬프) | 허용치 2 tick, 초과는 현재로 | 구현 |
| 입력 폭주 | 초당 20회 토큰 버킷, 같은 상태 반복 거부 | 구현 |
| 메시지 변조·과대 | 엄격 파싱, 1 KB 상한 | 구현 |
| 고스트 위조 | 서버 재시뮬레이션, 형식·교대·정렬 검사 | 구현 |
| 자동 입력 매크로(완벽 타이밍) | D 는 시드에서 계산 가능하므로 원리상 막기 어렵다. 입력 타이밍 통계 이상 탐지 필요 | **미구현** |
| 계정·평판 | 익명 매치만 있음 | **미구현** |

## 7. 배포/운영
| 구성 | 위치 | 비고 |
|---|---|---|
| 클라이언트 (정적) | Vercel | 글로벌 CDN, 프리뷰 배포 |
| 서버 (룸 상태 유지) | 상시 실행 컨테이너 (`apps/server/Dockerfile`, 단일 번들 파일) | 룸 상태가 프로세스 메모리에 있으므로 같은 룸의 모든 연결이 한 인스턴스에 붙어야 한다. 수평 확장 시 룸 단위 라우팅 필요. 서버리스 WebSocket 은 이 조건을 보장하기 어렵다고 판단(미검증) |
| 지역 | 클라이언트 CDN + 지역별 서버 (후속) | 지연 중요 |
| 분석 | 이벤트 로깅 (진행, 탈락 원인, 광고 노출) | SDK 선택 미정 |

## 8. 광고/배포 채널 (미결)
- 웹 광고: 일반 웹 광고 네트워크 vs 게임 포털 SDK(Poki, CrazyGames 등)의 수익/조건 차이를 조사해야 한다. **조건은 검증하지 않았음.**
- 포털 입점 시 SDK 요구(로딩, 광고 호출 규칙)가 달라지므로 `AdsService` 추상화를 유지한다.
- 앱스토어 배포가 필요하면 Capacitor 등 래핑 + 모바일 광고 SDK 분기.

## 9. 개발 단계 (제안)

| 단계 | 산출물 | 기간 가설 |
|---|---|---|
| M0 | 저장소 세팅, `sim` 코어 + 결정론 테스트 | 작은 단위 |
| M1 | Play 씬: 달리기/정지/술래 사이클, 판정 표시 (그레이박스, 아트 없음) | 핵심 검증 |
| M2 | Close Call/콤보/점수, 탈락 리플레이 | |
| M3 | 스테이지 30개 데이터, 봇, Assist | |
| M4 | 상점/스킨, 광고 연동, 저장, i18n | |
| M5 | 계측, 폴리시, 프리뷰 배포, 소프트런치 | |
| M6+ | 고스트 레이스 → 실시간 매치 | |

M1 시점에 **가속 구조의 재미 검증**(GDD 미결 1번)을 먼저 한다. 재미가 안 나오면 이후 비용이 크게 늘기 전에 룰을 수정한다.
